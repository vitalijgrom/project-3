# Дашборды доступности сайтов и почтовых узлов

Статические дашборды по данным мониторинга: скрипт раз в 5 минут обходит сайты
и почтовые хосты и пишет результат в Google Таблицу, а этот проект показывает,
что там происходит. Данные забираются через прослойку на Cloudflare,
отображаются без серверного рендеринга и без внешних библиотек.

**Живая цепочка данных:** Google Таблица → Cloudflare Pages Function
(`/api/monitor`) → браузер.

## Что показывает

Два контура — **Сайты** и **Почтовые узлы** — переключаются вкладками; вёрстка
и логика у них общая, различаются только листы таблицы. Сводка по обоим
контурам видна всегда, независимо от выбранной вкладки.

| Блок | Что отвечает |
|---|---|
| Сводка сверху | доступность каждого контура за весь период и сколько узлов не отвечает сейчас |
| KPI-строка | доступность, узлов под наблюдением, недоступны сейчас, медианная задержка, сбоев в журнале |
| Состояние узлов сейчас | плитка по всем узлам: кто отвечает, кто нет, кто помечен проблемным |
| Надёжность узлов | доля неудачных проверок за всю историю, худшие сверху |
| Причины недоступности | тайм-аут, DNS, TLS, недоступный адрес — и отдельно квоты Apps Script |
| Задержка ответа | распределение по корзинам, медиана и худший узел |
| Состояние SSL | что вернула проверка сертификата |
| Доступность по дням | столбцы по дням: высота — сколько было проверок, красная часть — сбои |
| Календарь отказов | тепловая карта день × час, видно и точный час аварии, и «проверок не было» |
| Активность мониторинга | сколько записей журнала какого типа и уровня |
| Таблица | все узлы с фильтрами, сортировкой и выгрузкой в CSV |

Фильтры (поиск, состояние, SSL, причина отказов, «только проблемные», «только
со сбоями») пересчитывают всё, что построено **по узлам**, включая KPI.
Карточки, построенные по журналу целиком — «Доступность по дням», «Календарь
отказов» и «Активность мониторинга», — фильтрам по узлам не подчиняются, потому
что журнал агрегирован по контуру, а не по хостам; на карточках об этом
написано.

Дашборды подхватывают тему системы, имеют собственный переключатель
светлая/тёмная и раз в 5 минут тихо обновляют данные.

### Про «квоту Apps Script»

Часть отказов в журнале — не отказы наблюдаемых узлов, а отказы самого
мониторинга: `Служба была вызвана слишком много раз за день: urlfetch`. Такие
записи выделены в отдельную причину и покрашены как предупреждение, а не как
падение узла: сайт в этот момент, скорее всего, был жив.

## Структура

```
public/
  index.html            разметка
  assets/styles.css     токены светлой и тёмной темы, компоненты
  assets/app.js         загрузка, фильтры, рендер всех карточек
  data/fallback.json    снапшот агрегатов на случай недоступности прослойки
functions/
  api/monitor.js        Cloudflare Pages Function — прослойка к Google Sheets
scripts/
  snapshot.mjs          обновление снапшота (переиспользует код функции)
wrangler.toml           конфиг Pages: каталог сборки и переменные
```

## Как работает прослойка

`functions/api/monitor.js` отвечает на `GET /api/monitor`:

1. Ходит в `gviz/tq` Google Таблиц и приводит ответ к стабильной JSON-схеме
   (`{ ok, source, fetchedAt, period, scopes[], config }`).
2. Кэширует ответ на edge Cloudflare — Google отдаёт `no-store`, поэтому TTL
   держим сами (`CACHE_TTL`, по умолчанию 300 секунд).
3. Отдельно хранит **последний удачный ответ**. Если Google лёг, отдаётся он
   с заголовком `x-cache: STALE` — дашборд не белеет, а честно пишет об этом.
4. Не пускает ID таблицы в браузер: фронтенд знает только про `/api/monitor`.

Полезные заголовки ответа: `x-cache` (`HIT` / `MISS` / `BYPASS` / `STALE`) и
`x-data-source`. Принудительно обновить: `GET /api/monitor?refresh=1` — это же
делает кнопка «Обновить».

Если прослойка недоступна (например, открыли `public/` как статику), дашборды
загружают `data/fallback.json` и показывают баннер о том, что данные снапшотные.

### Почему журналы не едут в браузер целиком

В листах журналов больше 600 000 строк — это десятки мегабайт, и ни браузеру,
ни воркеру их не потянуть. Поэтому агрегаты считает сам Google: прослойка шлёт
девять `gviz`-запросов с `group by`, и каждый возвращает сотни строк вместо
сотен тысяч.

| Запрос | Что даёт |
|---|---|
| лист «Статус …» целиком | текущее состояние узлов, SSL, задержка, примечание |
| `group by year, month, day, hour, C` | часовой ряд доступности → календарь и столбцы по дням |
| `group by year, month, day, B, C` | события журнала по дням, число запусков, пропуски |
| `group by D` по событию отказа | точные счётчики отказов **по узлам и причинам** |
| лист «Настройки» | списки наблюдаемых и помеченных проблемными узлов |

Последний запрос — главный трюк. Имя узла лежит внутри JSON-контекста, а `gviz`
не умеет группировать по подстроке. Но контекст отказа — это готовая строка
JSON, и разных её значений всего несколько сотен (узел × причина), поэтому
обычный `group by` по колонке контекста даёт точную статистику по узлам за всю
историю одним запросом.

**Чего в данных нет.** Журнал не разложен по узлам во времени, поэтому
доступность конкретного узла по дням построить нельзя. Отсюда деление:
«сколько отказов у узла» — точно и за всю историю; «как менялась доступность» —
по контуру целиком. Под фильтром KPI доступности переключается на оценку
`узлов × запусков` и подписывает это в подсказке.

## Требования к Google Таблице

* Доступ: «Любой, у кого есть ссылка — читатель». Ничего публиковать в веб
  отдельно не нужно, `gviz` работает по этому же доступу.
* Пять листов с ожидаемыми именами:

| Лист | Что в нём |
|---|---|
| `Статус сайты` | Сайты · Статус · SSL · Задержка (мс) · Примечание/Ошибка · Обновлено |
| `Статус почты` | то же для почтовых хостов |
| `Логи сайты` | Timestamp · Уровень · Событие · Контекст(JSON) |
| `Логи почты` | то же для почтовых хостов |
| `Настройки` | A — сайты, B — проблемные сайты, C — почты, D — проблемные почты |

* Колонки читаются по позиции (A…F), первая строка — заголовки.
* В журналах опознаются события `Сайт доступен` / `Сайт недоступен`,
  `Хост доступен` / `Хост недоступен`, `Единый запуск: сайты вычислены` /
  `Единый запуск: почты вычислены` и всё, что содержит «пропуск».
* Контекст отказа — JSON с ключами `url` (или `host`) и `примечание`.

Имена листов, событий и ключей контекста собраны в константе `SCOPES` в
`functions/api/monitor.js`: если в таблице что-то назовут иначе, править нужно
там, в одном месте.

## Деплой на Cloudflare Pages

Пошаговая инструкция со всеми настройками, подключением поддомена, закрытием
доступа и диагностикой — в **[DEPLOY.md](DEPLOY.md)**. Коротко:

1. Cloudflare Dashboard → **Workers & Pages** → **Create** → **Pages** →
   **Connect to Git**, выбрать этот репозиторий.
2. Настройки сборки:
   * Framework preset — **None**
   * Build command — оставить пустым
   * Build output directory — **`public`**
3. Deploy. Каталог `functions/` Cloudflare подхватывает сам — `/api/monitor`
   появится без дополнительной настройки.

Переменные `SHEET_ID` и `CACHE_TTL` заданы в `wrangler.toml`. Для Pages этот
файл — источник истины: в дашборде переменные видно, но редактировать их
нельзя. Чтобы управлять ими из интерфейса, удалите блок `[vars]` и задайте
значения в **Settings → Variables and Secrets** отдельно для Production и
Preview.

Разовый деплой из командной строки:

```bash
npm install
npx wrangler pages deploy public
```

Домен подключается в **Custom domains** проекта. Дашборд внутренний — закройте
его **Cloudflare Access**; в разметке уже стоит `noindex, nofollow`.

## Локальная разработка

```bash
npm install
npm run dev          # wrangler pages dev public → http://localhost:8788
```

`wrangler pages dev` поднимает и статику, и функцию, поэтому `/api/monitor`
работает локально ровно так же, как в проде.

Без wrangler можно открыть просто статику (`npx serve public`) — дашборды
переключатся на снапшот и покажут об этом баннер.

Обновить снапшот:

```bash
npm run snapshot
```

## Настройка под себя

* **Контуры, листы и события** — `SCOPES` в `functions/api/monitor.js`.
  Третий контур добавляется одним элементом массива: фронтенд рисует вкладки
  по тому, что пришло, и ничего про «сайты» и «почты» не знает.
* **Причины отказов** — `REASONS` там же. Порядок важен: проверки идут сверху
  вниз, первое совпадение выигрывает, поэтому квоты стоят перед тайм-аутом.
* **Корзины задержки и пороги календаря** — `LATENCY_BINS` и `HEAT_BINS` в
  `public/assets/app.js`. Шаги неравномерные: у мониторинга жёсткий лимит
  7 секунд, и всё, что дольше пяти, одинаково плохо.
* **Частота автообновления** — `CONFIG.autoRefreshMs`.
* **Палитра** — CSS-переменные в начале `public/assets/styles.css`. Цвет здесь
  семантический (доступен / недоступен / предупреждение), но нигде не остаётся
  единственным носителем смысла: рядом всегда знак и подпись. Тепловая карта
  использует одну тёплую шкалу (на тёмной теме она развёрнута, чтобы «больше»
  оставалось заметнее фона).
